## 1. Превью новых элементов (ГЛАВНЫЙ)

**Что было.** Кадр появлялся, а через минуту исчезал в плейсхолдер. Причина не «не грузится», а
подмена: после аплоада картинка выносится в `assets/elements/<id>.jpg?v=N`, локальный dataURL в
записи элемента заменяется на этот путь, и следующий ре-рендер ставит `src` на файл, которого
GitHub Pages ещё не раздаёт (билд не прошёл — см. п. 3). Картинка «пропадала» ровно в момент синка.

**Что сделано** (`index.html`):

- `state.previewCache` — локальный кэш захваченных кадров (dataURL), до 14 штук / 3 МБ,
  переживает перезагрузку (localStorage). Пишется в трёх точках: `addElement`,
  `handleImagePaste` (после обрезки), `completeCalibration`, и — главное — в
  `applyPreparedAssetUrlsToCatalog`, то есть **ровно перед** тем, как `element.image`
  меняется с dataURL на ещё не опубликованный путь.
- `state.previewResolved` — карта «этот URL уже реально отрисовал этот кадр». Ре-рендер
  никогда не понижает работающую картинку до неопубликованной ссылки.
- `previewSourceList()` — цепочка источников: уже сработавший URL → локальный кадр →
  `assets/...?v=N` → тот же путь без `?v` → `raw.githubusercontent.com/.../main/assets/...`.
  Последнее важно: raw отдаёт файл **сразу после коммита**, без билда Pages.
- `probePublishedPreview()` — фоновая проверка `new Image()`: подмена на опубликованный URL
  происходит только после успешного `onload`, и только тогда локальная копия выбрасывается.
- Обработчик `error` на картинках идёт по цепочке дальше, обработчик `load` фиксирует рабочий URL.

**Проверено.** Self-test: `previewSourceList` после «внешнелизации» отдаёт первым захваченный
кадр; разметка карточки содержит `data:image/jpeg`. В браузере: 35/35 картинок реально
загружены (`naturalWidth > 0`), плейсхолдеров «Кадр недоступен» — ноль.

## 2. Сброс текста при вводе (ГЛАВНЫЙ)

**Что было.** Входящий sync затирал недописанное описание.

**Что сделано:**

- Поле в фокусе неприкосновенно: `applyRemoteSnapshot` откладывает снапшот, если
  `isTextEditing()` **или** с последнего нажатия клавиши прошло меньше 1.2 с (`isTypingPause`).
  Это же условие добавлено в `canApplyRemote()`.
- `state.drafts` — черновик каждого правленого поля (значение + время). После применения
  удалённого снапшота `restoreDrafts()` возвращает локальное значение поверх чужого,
  дописывает его в ту же транзакцию IndexedDB и помечает каталог грязным, чтобы оно уехало
  в облако. **Текст не теряется никогда**, даже если снапшот пришёл в момент blur.
- Конфликт показывается тостом («Ваш текст сохранён: партнёр правил description»), без потери
  текста и без модалок.
- Отдельно закрыта гонка: ответ GET, стартовавший до нашей записи, больше не применяется
  (`state.cloud.writeGeneration`) — раньше он мог откатить каталог к состоянию «до записи».

**Проверено.** Сквозной сценарий в браузере: набираем текст → сервер отдаёт снапшот с чужим
текстом в этом же поле → через 7 с (2 цикла опроса) поле не изменилось; после blur и ещё 8 с
значение по-прежнему наше. `draftWhileFocused: true, draftAfterSync: true`.

## 3. Presence-шторм и частота коммитов (КОРЕНЬ БЕД)

**Что было.** Каждый клиент коммитил `presence.json` раз в 30 с. GitHub Pages даёт ~10 билдов
в час — сегодня 29 билдов подряд `errored`, фиксы не доезжали до сайта.

**Что сделано:**

- Presence **полностью убран из репозитория**. Ни одного PUT/POST ради «N онлайн».
  Механика: BroadcastChannel + localStorage-heartbeat (вкладки одного браузера, мгновенно),
  плюс честный признак «партнёр активен» — если за последние 3 минуты прилетела чужая правка
  каталога (это и так видно из опроса `data.json`, лишних запросов ноль). В подсказке к счётчику
  написано, сколько вкладок своих и был ли партнёр.
- Файл `presence.json` удалён из репозитория.
- Коммиты данных забатчены: `CLOUD_PUSH_DELAY = 45 c`, минимум 45 с между пушами,
  потолок отсрочки 90 с (при непрерывном наборе), плюс досрочная отправка по blur.
  Клик по индикатору сохранения — «отправить сейчас».
- Опрос облака 2 с → 3 с (условный GET по ETag, 304 не тратит лимит API).
- При уходе со страницы с неотправленными правками — предупреждение браузера.

**Найденная и починенная по дороге регрессия (важно).** Первая версия батчинга не отправляла
данные **никогда**: опрос каждые 3 с вызывал `scheduleCloudSave()`, который сбрасывал таймер на
новые 45 с. Замерено в браузере: 70 с — ноль отправок. Исправлено (дедлайн отправки нельзя
отодвинуть, только приблизить). Повторный замер: ровно одна отправка на ~50-й секунде.

**Цифры.** Было: ~120 коммитов/час presence на двух клиентах + коммит на каждую правку.
Стало: 0 presence-коммитов, не чаще ~80 коммитов данных в час на клиента в худшем случае
непрерывной работы, реально — единицы.

## 4. Таймкоды при захвате

Сделано в предыдущем коммите сессии и сохранено: в рабочую область встроен YouTube-плеер
активного ролика, таймкод берётся из `player.getCurrentTime()` **в момент захвата**, до любой
асинхронной работы с картинкой; запасные источники — `<video>` на странице, текст/URL из буфера
обмена, OCR строки `0:51 / 15:02` со скрина. Полностью удалена старая «автонумерация» таймкодов
(`index * 1.5`), которая и давала расползающийся сдвиг.

## 5. Исправление старых таймкодов данными

Применена таблица `OTCHET-timecode-ocr.md`: 18 распознанных элементов, из них 16 исправлено,
2 уже были верны, 0 расхождений с базовыми значениями отчёта (сверка шла по id и по старому
значению — если бы кто-то успел поправить руками, элемент был бы пропущен и указан здесь).
4 элемента `UNREADABLE` не тронуты. Диff `data.json` — ровно 16 строк, только `timecodes`.

Примеры: `#19` 0:27 → 0:51, `#22` 0:32 → 0:55, `#13` 0:18 → 0:32.

**Риск.** Если у кого-то сейчас открыта вкладка со старым кодом и несохранёнными правками, при
её отправке 3-way merge может вернуть старые таймкоды (её локальное значение отличается от базы).
**После деплоя обеим машинам нужно перезагрузить страницу** — тогда данные подтянутся из облака.

## 6. Защита от удаления

- Удаление ролика — модалка с обязательным вводом слова `УДАЛИТЬ`, кнопка до этого
  заблокирована; в тексте написано, сколько элементов будет уничтожено.
- Удаление элемента — модалка-подтверждение (осознанный второй клик), без ввода слова.
- Случайный клик по корзине ничего не удаляет ни в одном из двух случаев.

Проверено в браузере: у модалки элемента поля ввода нет и кнопка активна; у модалки ролика поле
есть и кнопка заблокирована.

## 7. Отсылки #NN как связи между элементами

- Любое `#NN` в тексте элемента (описание, техника, название, мнение, применение) в режиме
  просмотра — кликабельная подсвеченная ссылка: скролл к кадру + подсветка на 2.2 с.
  В режиме редактирования текст остаётся обычным текстом.
- На карточке показываются обратные связи: «упоминается в: #12, #24» (кликабельно).
- Связи **не хранятся**, а вычисляются из текстов на лету; номер = позиция в хронологической
  сортировке (`elementsForProject` → `chronologicalElements`), то есть та же нумерация, что на
  карточках и в поиске.
- Ссылка на несуществующий номер остаётся обычным текстом, ссылка на себя не считается.

**Риск, о котором просили предупредить.** Номера — позиционные. При удалении элемента из середины
ролика все последующие номера сдвигаются, и написанные руками `#NN` в чужих описаниях начнут
указывать на соседа. Это свойство самой нумерации, а не реализации связей. Лечится только
переходом на неизменяемые номера (например, порядковый номер, выдаваемый при создании и не
переиспользуемый) — это отдельная задача, без спроса не трогал.

## 8. Статус-бар, статистика и живой UI

- **Левая панель больше не дёргается**: список роликов патчится на месте (класс, `--progress`,
  проценты, счётчик), а не перерисовывается через `innerHTML` при каждом синке. Полная
  перерисовка — только если реально изменился состав или порядок списка.
- **Шапка не прыгает**: у индикатора сохранения и счётчика онлайна фиксированная ширина и
  табличные цифры. Тексты: «Сохранено» / «В очереди» / «Отправка…» / «Ошибка: …» — читаемым
  текстом, полная формулировка в подсказке, клик — отправить сейчас.
- **Панель статистики по текущему ролику** (кнопка «📊 Статистика» под параметрами ролика):
  разбивка по категориям (количество + доля + полоса), сумма повторов ×N, «Размечено N/M»,
  покрытие таймлайна — теперь честное: последний таймкод против длительности (`0:55 из 15:02 · 6%`),
  а не бывшая формула «элементов × 1.5 с».
- **Новый блок «Повторения приёмов»**: топ по упоминаниям `#NN` в текстах (с указанием, кто
  ссылается) и топ по ×N. Номера в блоке кликабельные.
- График роликов больше не переигрывает анимацию при каждом обновлении (это и была часть «дёрганья»).
- **Бейдж повторов ×N греется**: вес = ×N + число ссылок `#NN` на этот кадр. Цвет идёт
  серый → синий → зелёный → жёлтый → оранжевый → красный, растёт кегль и насыщенность.
  Обновляется на месте, без перерисовки сетки — при клике по бейджу и при уходе из текстового поля.

## Что осталось / на что смотреть

1. **Перезагрузить страницу на обеих машинах** после деплоя — иначе старые вкладки продолжат
   коммитить presence и могут откатить исправленные таймкоды.
2. Позиционная нумерация `#NN` сдвигается при удалении элементов (см. п. 7).
3. Файлы `OTCHET-autorazmetka-pilot.md`, `pilot-elements.json`, `SRAVNENIE-pilot.md` в рабочем
   каталоге не мои — оставлены неотслеживаемыми, не коммитил.
4. Токен GitHub по-прежнему зашит в `index.html` и виден в публичном репозитории. Это вне рамок
   задачи, но это дыра: любой может писать в репозиторий. Лечится только переносом записи на
   какой-нибудь прокси/функцию.
